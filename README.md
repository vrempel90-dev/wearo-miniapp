# WEARO

Мультивендорный fashion-маркетплейс: Next.js + TypeScript + Tailwind, PostgreSQL,
Prisma, Telegram Mini App, Zod и S3. Модульный монолит, русский интерфейс, цены в ₸.
Одна корзина создаёт отдельный заказ каждому магазину.

## Локальный запуск

Нужен Node.js 24. Установка: `npm ci`. В первом терминале запустите `npm run db:local`.
Это настоящая PostgreSQL на 127.0.0.1:55439; пароль генерируется и сохраняется только
в игнорируемой папке work. При первом запуске создаётся .env с wearo_dev и wearo_test.
Оставьте терминал открытым. Во втором терминале:

```sh
npm run db:migrate
npm run db:seed
npm run dev
```

Откройте http://localhost:3000/account. Тестовые профили: покупатель, администратор,
два независимых продавца. Seed запускается повторно без дублирования демонстрационных
товаров; не создаёт продаж. DEMO_SEED и DEV_AUTH разрешены только вне production.
Фотографии без S3 не загружаются: UI показывает заглушку, не фальшивую фотографию.
Альтернатива: compose.yaml или собственная PostgreSQL и DATABASE_URL.

## Рабочие сценарии

Покупатель: `/`, `/product/:id`, `/favorites`, `/cart`, `/orders`, `/account`.
Продавец подаёт заявку в кабинете, администратор одобряет её в `/admin`.
`/seller` содержит профиль, создание/редактирование товара, варианты, остатки,
фотографии и обработку только собственных заказов. Все изменения товара требуют
повторной модерации. Комиссия задаётся в базисных пунктах: 1000 = 10%.

Уже резервированные единицы не включаются в доступный остаток. Изменение доступного
остатка не снимает резерв. Денежные суммы хранятся целыми тиынами (1 ₸ = 100), цены
и комиссионная ставка копируются в OrderItem/Commission при оформлении.

Оформление работает в SERIALIZABLE-транзакции с ограниченным повтором конфликтов.
Уникальный (userId, idempotencyKey) исключает дубли. Возврат резерва и история
статусов находятся в той же транзакции. Доставка требует перевозчика и трек-номера.
Покупатель запрашивает возврат доставленного заказа, администратор одобряет его и
подтверждает получение. Остаток восстанавливается только при получении возврата.

## Telegram и первый администратор

Укажите TELEGRAM_BOT_TOKEN и публичный HTTPS APP_URL; настройте Mini App через
BotFather или выполните `npm run bot:configure` (изменяет кнопку меню вашего бота).
Передаётся `initData`, сервер проверяет HMAC, возраст (5 минут), дубликаты и replay.
`initDataUnsafe` не используется. Случайная HttpOnly-сессия хранит в БД только хеш
токена, действует 24 часа, Secure в production; роль читается из БД на каждом запросе.

Первый администратор: установите BOOTSTRAP_ADMIN_TELEGRAM_ID на ваш контролируемый
Telegram ID и выполните `npm run admin:bootstrap`. Команда не доступна через HTTP,
пишет AuditLog; затем уберите идентификатор из окружения. Веб-регистрация не выдаёт ADMIN.

## Фото и платежи

Настройте S3_ENDPOINT, S3_REGION, S3_BUCKET, S3_ACCESS_KEY_ID, S3_SECRET_ACCESS_KEY,
S3_PUBLIC_URL (HTTPS, публичный префикс объектов). Сервер ограничивает тело запроса
и файл, проверяет декодирование JPEG/PNG/WebP, число пикселей, удаляет метаданные,
перекодирует в JPEG и загружает в объектное хранилище. Чужие imageId не принимаются.
Контент-Length нужен для загрузки; повреждённые и слишком большие файлы отклоняются.
Настройте lifecycle для неиспользованных объектов и CORS только для вашего домена.

PaymentProvider — интерфейс намерения, проверки подписанного события и возврата.
Реальный провайдер отключён. TEST_PAYMENTS=true работает только вне production,
только для серверных isTest-заказов. TEST_SUCCEEDED отличается от PAID: реальные
обязательства и статистика продаж остаются нулевыми. Внешнего endpoint, способного
пометить заказ PAID по пользовательскому JSON, нет. Реальные отмены оплаченного
заказа и возвраты блокируются до подключения проверенного провайдера возвратов.

Переходы: PENDING → CONFIRMED → PROCESSING → SHIPPED → DELIVERED.
До отправки продавец/администратор может отменить заказ; покупатель — до сборки.
DELIVERED → RETURN_REQUESTED → RETURNED, либо DELIVERED после отклонения обращения.
Подтверждение заказа требует подтверждённой оплаты. Неоплаченные заказы без
подключённого провайдера остаются PENDING; их может отменить покупатель/администратор.

## Проверки

```sh
npm test
npm run test:integration
npm run typecheck
npm run build
npm run test:e2e
npm run test:production
npm audit --audit-level=high
```

Integration запускает Prisma reset **только** на локальной БД с именем wearo_test;
это намеренно отдельная тестовая база, все её данные будут очищены. Проверяет весь
сценарий двух продавцов, IDOR, модерацию, варианты, актуальные цены, комиссии,
конкурентные оформления и overselling, rollback, отмены, возвраты и Telegram replay.
E2E требует демо seed в development-базе; запускает отдельный dev-сервер, тестирует
реальные HTTP-сессии, полномочия, корзину и мобильный интерфейс.
Production smoke запускает собранный standalone на localhost:3110 и проверяет
healthcheck, статические файлы, отключение dev-login и отказ development-сессиям.

## Railway / production

Dockerfile формирует standalone Next.js, использует PORT и HOSTNAME=0.0.0.0;
railway.toml задаёт сборку и `/api/health` с проверкой PostgreSQL. Миграции запускаются
через `prisma migrate deploy` перед сервером; повторный старт применённых миграций
не повторяет. Не используйте migrate reset/db push в production.

Создайте постоянную PostgreSQL и задайте DATABASE_URL. Укажите HTTPS APP_URL,
TELEGRAM_BOT_TOKEN, S3-переменные, DEV_AUTH=false, TEST_PAYMENTS=false, DEMO_SEED=false.
Healthcheck отклоняет незавершённую/небезопасную конфигурацию. .env и work исключены
из Docker image. Файлы и PostgreSQL не хранятся на эфемерном диске приложения.

Настройте ежедневные резервные копии, отдельную offsite-копию и проверьте восстановление
в отдельной базе до публичного запуска. Инструкция Railway:
https://docs.railway.com/guides/postgres-backups-restores . Наличие конфигурации
не означает, что резервное копирование внешней базы уже настроено.

Перед запуском для реальных пользователей согласуйте размещение персональных данных,
согласия, сроки хранения и платёжную/юридическую схему. Railway сам по себе не
подтверждает соответствие требованиям Казахстана. Статья 12 закона о персональных
данных предусматривает хранение базы на территории Казахстана:
https://www.gov.kz/uploads/2021/7/12/8bd1ab6ec99fb5448ac343b0611e4829_original.110350.pdf .
Требуется проверка актуальной редакции и конкретной схемы размещения перед запуском.

## Границы проверки

Настроенная интеграция Telegram, доступность S3, развёртывание Railway, резервные
копии внешней базы и настоящий платёжный провайдер требуют отдельных credentials
и проверки. Локальный seed и тестовые оплаты их не подтверждают.
Тексты UI собраны в компонентах и словаре statusLabel; lang=ru. Для казахской
локализации можно вынести эти строки в словари без изменения моделей и API.
